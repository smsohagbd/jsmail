In-flight inspector
What “in-flight” means on disk vs workers

In-flight on disk ({{.QueueInflightCnt}} files): the dispatcher already claimed these messages from pending and wrote status=inflight to the JSON file. They are not all blocked on the IP pool.

Work channel: {{.WorkChLen}} of {{.WorkChCap}} slots are filled — those messages are waiting in memory for one of {{.Workers}} workers to pick them up.

Actively in SMTP: at most {{.Workers}} messages can be inside deliver() at once (connection attempts, DATA, etc.). The rest of in-flight is backlog in the channel.

Memory inflight map: {{.InflightMemory}} (should match disk inflight when steady). IP pool / throttle / 421 defer happens inside a worker; after defer the file becomes deferred and leaves in-flight.

Live delivery trace: {{.ActiveTraceCount}} message(s) currently inside deliver() on a worker — the Phase column shows where each one is spending time (not IP pool unless you see waiting_mx_semaphore, ip_pool_all_busy, tcp_dial_*, smtp_*, etc.).

~Queued for worker (approx): {{.WaitChannelApprox}} in-flight files with no trace yet = still in the work channel buffer, not stuck in IP pool logic.

Live phase labels: queued_work_channel = claimed by the dispatcher (in memory map) but not yet inside deliver(). orphan_disk = file says inflight but not in the claim map (should auto-repair to pending every 30s).

Last error is hidden for queued_work_channel rows — it was almost always from a previous defer, not the current wait. It still shows when there is a live trace or for orphan rows.
